# LiteClaw v0.2 持久化任务服务设计

## 目标

在现有 Agent Runtime 上增加可恢复的后台任务服务。用户可以通过 HTTP API 创建、查看、暂停、恢复和删除一次性或周期任务；到期任务调用现有 Agent Runtime，执行结果、错误和审批状态持久化到 SQLite。

## 范围

v0.2 包含：

- 一次性任务与固定间隔周期任务。
- SQLite 持久化任务定义和每次执行记录。
- 应用启动后恢复仍处于启用状态的任务。
- 创建、列表、详情、暂停、恢复和删除 API。
- 到期执行、有限重试、并发上限和优雅关闭。
- 复用现有 Agent Runtime、Planner、Tool Registry、Memory 和 Approval。
- 任务需要高风险审批时保存 `waiting_approval`，审批后继续原有 run。

v0.2 不包含 cron 表达式、分布式锁、多进程协调、跨机器队列、消息通知或可视化管理页面。这些内容不会进入本版本的接口承诺。

## 数据模型

新增 `scheduled_tasks`：

- `id`：任务 ID。
- `name`：用户可读名称。
- `session_id`：固定会话；创建任务时未提供则自动创建。
- `prompt`：每次到期发送给 Agent 的请求。
- `schedule_type`：`once` 或 `interval`。
- `run_at`：一次性任务的 UTC 时间。
- `interval_seconds`：周期任务间隔，最小 10 秒。
- `next_run_at`：下一次计划执行时间。
- `status`：`active`、`paused`、`completed` 或 `failed`。
- `max_retries`：单次触发最多重试次数，范围 0 到 5。
- `retry_count`：当前触发已经重试的次数。
- `last_error`、`created_at`、`updated_at`。

新增 `scheduled_task_runs`：

- `id`、`task_id`、`agent_run_id`。
- `status`：`running`、`waiting_approval`、`completed` 或 `failed`。
- `attempt`、`answer`、`error`、`started_at`、`finished_at`。

删除任务采用真实删除，并由外键级联删除任务执行记录；不会删除关联的会话、消息、Agent run 或长期记忆。删除 API 是明确操作，不由模型工具直接暴露。

## 组件边界

`app/tasks/models.py` 定义 API 与领域模型，只负责字段约束和调度参数校验。

`app/tasks/repository.py` 封装任务数据库操作，包括创建、领取到期任务、更新下次执行时间、保存执行记录以及启动恢复。

`app/tasks/scheduler.py` 维护单个后台循环。循环每秒查询到期任务，通过数据库的原子状态更新领取任务，并使用 `asyncio.Semaphore` 限制并发。它不包含 HTTP 逻辑。

`app/tasks/service.py` 负责执行一个任务：创建执行记录，调用 Agent Runtime，根据返回结果更新状态，计算重试或下一次周期时间。

`app/api/tasks.py` 仅负责 HTTP 输入输出和错误映射。

## 调度语义

所有时间以 UTC ISO 8601 保存。`once` 任务必须提供 `run_at`；`interval` 任务必须提供 `interval_seconds`，并允许提供第一次执行时间，未提供时使用创建时间加间隔。

每个进程只启动一个 Scheduler。任务领取采用 SQLite 事务，只有状态为 `active` 且 `next_run_at <= now` 的任务能从 `active` 原子切换到内部执行状态。应用异常终止后，启动恢复把超过租约时间的执行中任务重新放回 `active`。当前版本面向单进程 Uvicorn；多个 worker 不作为支持配置。

周期任务按上一次计划时间推进，若服务离线跨过多个周期，只补执行一次，然后把下一次时间推进到未来，避免启动后突发补跑大量任务。

## 执行、重试与审批

每次触发调用现有 `AgentRuntime.run(session_id, prompt)`。成功时保存回答。模型认证错误、模型不可用、最大步数和其他未处理异常都会写入执行记录。

失败时只对模型暂时不可用和非业务异常重试，重试延迟为 5、15、30、60、120 秒，且不超过 `max_retries`。认证失败、会话不存在和明确拒绝审批不自动重试。一次性任务重试耗尽后变为 `failed`；周期任务保留 `active` 并安排下一周期，同时记录本次失败。

若 Agent 返回 `PendingRunResult`，任务执行记录变为 `waiting_approval`。审批 API 恢复 Agent run 后，通过任务服务完成该执行记录并安排下一次周期。等待审批期间不会重复触发同一个任务。

## HTTP API

- `POST /v1/tasks`：创建任务，返回 201。
- `GET /v1/tasks`：按状态可选过滤并分页。
- `GET /v1/tasks/{id}`：返回任务和最近执行记录。
- `POST /v1/tasks/{id}/pause`：暂停后不再领取；正在执行的任务完成当前轮。
- `POST /v1/tasks/{id}/resume`：恢复并重新计算已过期的下一执行时间。
- `DELETE /v1/tasks/{id}`：删除任务定义和任务执行记录。

输入时间必须带时区。不存在返回 404；非法状态转换返回 409；字段错误由 FastAPI 返回 422。

## 生命周期和配置

FastAPI lifespan 在数据库初始化和 MCP 连接完成后启动 Scheduler，在浏览器和 MCP 关闭前停止 Scheduler，并等待正在执行的任务在可配置超时内退出。

新增配置：

- `LITECLAW_TASKS_ENABLED=true`
- `LITECLAW_TASK_POLL_SECONDS=1`
- `LITECLAW_TASK_MAX_CONCURRENCY=2`
- `LITECLAW_TASK_SHUTDOWN_TIMEOUT=15`
- `LITECLAW_TASK_LEASE_SECONDS=300`

测试中可关闭真实后台循环，并直接调用单轮 `tick()` 保证确定性。

## 可观测性

结构化日志新增 `task.created`、`task.claimed`、`task.run_completed`、`task.run_failed`、`task.waiting_approval`、`task.paused` 和 `task.resumed`。日志包含 `task_id`、`task_run_id`、`agent_run_id`，不记录完整 prompt。

`/health` 新增任务调度器状态、正在执行数量和最后一次 tick 时间。

## 测试与验收

单元测试覆盖调度参数校验、一次性时间计算、周期追赶、重试分类、重试上限和状态转换。

仓储测试使用临时 SQLite，验证创建、原子领取、暂停恢复、启动恢复和级联删除。

服务测试使用 FakeModel，验证到期任务完成、失败重试、等待审批和审批后完成。

API 测试验证所有路由、404、409、分页和持久化重启。

手工验收创建一个 2 分钟后执行的 FakeModel 任务，重启服务后确认任务仍执行；再创建一个需要文件覆盖审批的任务，确认它返回等待审批并在批准后完成。
