# LiteClaw v1.2 聊天记录分析设计

## 目标与范围

用户可以导入自己取得的微信聊天记录，按会话或时间查看活动、待办、沟通观察，并生成周报、月报、年报。输入为 TXT、CSV、JSON 文件；不读取微信进程、登录态或加密数据库。所有分析只依据已导入消息，不把推断表述为事实诊断。

## 方案选择

1. **仅用大模型直接读取文件**：实现快，但大文件会超上下文，难以删除、检索和核对证据。
2. **本地规范化消息 + 确定性统计 + 可选模型分析（采用）**：支持完整导入和重复导入去重，结果可回溯消息；没有模型时仍能给出基本活动与事项线索。
3. **直接连接微信本地数据库**：依赖版本与密钥提取，维护和隐私风险高，不作为本版输入路径。

## 数据与归属

- `chat_sources` 保存导入批次、文件名、格式、会话名、用户在该会话中的名称、导入时间与数量。
- `chat_messages` 保存规范化 UTC 时间、发送者、文本、来源行号及稳定去重指纹。默认时区为 `Asia/Shanghai`，可在导入时指定 IANA 时区。
- 每个来源继承当前 API 主体的 `owner_id`。RBAC 下普通用户只能访问自己的来源与消息；管理员可查看全部并在导入时指定已存在的用户。旧式无归属数据不存在于新表。
- 原文件不持久化。删除来源时级联删除其消息；同一来源重复上传通过指纹避免消息重复。只接受文本内容，附件占位会保留为文本但不会读取附件。

## 导入契约

- `POST /v1/chat-records/import` 接受原始文件字节，查询参数为 `filename`、可选 `conversation`、`self_sender`、`timezone`、`owner_id`。格式由扩展名确定。
- TXT 支持 `[2026-10-01 09:30] 张三: 内容` 与 `2026-10-01 09:30:00 张三: 内容`，非头部行续接上条消息。CSV/JSON 支持常见中英文列名：时间、发送者、内容、会话。JSON 支持数组或 `{ "messages": [...] }`。
- 最大 10 MiB、50,000 条消息。编码按 UTF-8 BOM、UTF-8、GB18030 尝试；格式错误、无有效消息或超限返回明确 4xx，整个导入不落库。导入结果返回来源 ID、读取条数、去重条数与时间范围。

## 分析与报告

- `GET /v1/chat-records/sources`、`GET /v1/chat-records/messages` 支持按所有者、来源、会话、时间分页；消息 ID 可用于回查原文。
- `POST /v1/chat-records/analyze` 可指定来源、会话、联系人、时间范围，返回消息数量、参与者、活动趋势、未完成事项线索、沟通观察。每条事项和观察都带消息 ID、原文摘录和置信说明。
- 事项状态从上下文区分提出、进行中、完成、取消；不能确认状态时标记为“待核实”。“对方是什么人”仅描述在该聊天中可观察到的沟通方式，不作人格或心理诊断。
- `POST /v1/chat-records/reports` 接受 `week`、`month`、`year` 和日期，按本地日历边界生成周期报告。报告包含活动、已完成、待跟进、沟通复盘、数据覆盖范围和证据消息 ID。只有用户本人发送的消息才会成为用户工作成果；他人消息可作为背景与待办来源。
- 配置真实模型时，通过受限长度、明确数据边界的提示词生成叙述性观察；模型输出必须是结构化 JSON，引用 ID 必须存在于选定消息中。不符合结构或引用不存在时回退确定性分析。FakeModel 或无 Key 时返回确定性统计和待核实事项，不捏造对方特征。

## 使用界面

- `/chat-records` 提供本地页面：选择文件与会话信息、上传、浏览来源与消息、选择范围运行分析、生成周月年报、删除导入批次。页面对 API Key 使用当前标签页 `sessionStorage`，与现有 Eval 页面习惯一致。页面文本说明聊天分析的证据范围。

## 错误处理与验收

- 任何跨用户来源或消息访问返回 404；列表不混入其他用户数据。报告与分析查询同样应用 owner 过滤。
- 不把聊天内容写入日志或错误消息，不在 API 响应中返回原上传文件。删除后对应消息和派生查询结果消失。
- 用实际格式样例验证多行 TXT、CSV、JSON、时区、重复导入、错误原子性、RBAC、事项状态和周月年边界；全量旧测试保持通过。
